# FAQ

## 為什麼不直接推出應用程式？ {#why-not-just-ship-an-app}

因為應用程式是容易的部分，困難的部分是共用的。建立在他人有損格式函式庫上的文書處理器，將永遠繼承其資料遺失的 bug：每次透過該函式庫進行 roundtrip，未建模的部件都在擲骰子賭運氣。文件引擎*本身*才是護城河——具備機器強制檢查準則的無損 OOXML 處理，加上讓原生與瀏覽器渲染保持一致的排版核心。作為可重用的引擎（同一核心未來將承載 XLSX 與 PPTX），這比綁定在單一 UI 上更有價值，這也是程式庫目前提供 CLI head 與瀏覽器展示而非終端使用者應用程式的原因：外殼刻意設計為包覆引擎的輕量介接層，因此無論誰來打造應用程式——包含我們自己——都能直接繼承這些保證，而不需重新打造。

具體而言，「目前尚未推出應用程式」階段換來的是：

- **可驗證的承諾。** `roundtrip --check` 是交付物。應用程式會隱藏檔案是否變更；CLI 閘門則印出 byte-identical 計數。
- **第一天起就具備兩種外殼。** 雙目標規則（原生 + wasm32，在 CI 中驗證）是瀏覽器 demo 在骨架階段就得以存在的原因——將 wasm 事後硬塞進應用程式形態的程式碼庫，往往是專案夭折的途徑。
- **低成本的外殼拆分。** 分層規則的強制執行意味著未來的應用程式可以存在於自己的程式庫中，不需對引擎進行解耦。

## 格式路線圖為何？ {#what-is-the-format-roadmap}

Quire 是 **Office 格式引擎家族**，而非只有野心的 DOCX 專案。立論基礎在於：DOCX/XLSX/PPTX 共享大部分最困難的環節——OPC 封包容器（ZIP+XML，在位元組層級無損）、OOXML 部件處理以及無損準則本身——因此每個新格式都是同一核心上的同級 crate（`core/xlsx`、`core/pptx`），僅保留其格式所要求的排版模型：DOCX 為流式（flow）、XLSX 為網格（grid）、PPTX 為畫布（canvas）。

| 里程碑 | 範疇 |
|---|---|
| **目前** | DOCX：無損 roundtrip + 排版／分頁（本程式庫） |
| **進行中** | XLSX：基於相同 OPC 容器與 roundtrip 閘門的 `core/xlsx`——80 份具單檔授權語料庫與 byte-identical roundtrip 閘門已收齊，讀取模型現已涵蓋工作表模型、儲存格投影（sharedStrings 上五種值型別）與樣式級聯（字型／填充／邊框／數字格式解析為 effective 樣式）；下一步為公式引擎 |
| **下一步** | DOCX 深度：editing API（變更操作 + 無損存檔鏈）、剩餘渲染缺口——依語料庫失敗分群排序；loro 介接插槽背後的 CRDT 協同層 |
| **後續** | PPTX：`core/pptx`——重用排版與塑形的投影片／形狀模型；具備自身的簡報渲染清單 |
| **規劃中（排在 PPTX 之前）** | ODF 家族：`core/odf`——ODT 優先，其後為 ODS/ODP，遵循相同的無損容器準則。50 檔 ODT 語料庫（逐檔授權、容器級普查並點名三檔違例樣本）已與代碼錨定版設計書一併落地；容器 crate 正依紅燈考卷建置中。誠實範疇：ZIP 層與 roundtrip 閘門可沿用；OOXML 部件模型不可重用。`text:sect` 與 `office:styles` 從 OASIS 規格映射，而非從 DOCX 猜測。 |
| **規劃中** | Legacy DOC（舊版 Word 二進位）：OOXML 之前的格式住在 OLE compound file 而非 OPC——走自己的解析線，下游沿用同一套排版與整形 crate，先做唯讀渲染。誠實範疇：MS-DOC 的歷史包袱比 OOXML 重，缺口由語料普查先點名，不由程式碼先猜。 |

開放格式與 OOXML 並列為第一級家族目標，而非事後補充：相同的核心、相同的無損標準，並以 LibreOffice 作為兩者的客觀基準。

基於該引擎構建的產品線（一旦各自發布獨立版本即各自獨立程式庫）：瀏覽器編輯器、基於原生核心的 Tauri 桌面應用程式，以及可自架的協同／儲存伺服器（Docker 優先，與其他一切一樣採 Apache-2.0 授權）。全數規劃中——請參閱公開路線圖：[quireoffice.dev/roadmap](https://quireoffice.dev/roadmap)。

外殼策略：外殼保留在主樹內，直到其中之一發布自身的獨立版本（安裝檔／部署的應用程式）、授權條款分歧或貢獻者社群分歧——分層閘門正是維持拆分低成本的關鍵。

## 為什麼使用 400 份檔案的語料庫而非單元測試？ {#why-a-400-file-corpus-instead-of-unit-tests}

因為 DOCX 的資料損失發生在長尾效應中：Apple Keynote 匯出檔案中的 ZIP64、無人記錄的廠商 `extra` 欄位、fuzzer 產生的 CRC 損壞佈景主題、1998 年 Word 6 的特殊古怪行為。單元測試只能斷言作者所想像的情況；本語料庫斷言的是真實世界產出的內容：

- **130 份 phase-0 檔案** —— 真實 bug 回報檔案（LibreOffice、POI——上游已匿名化）、公開功能範本（Open-Xml-PowerTools、PHPWord）、微軟官方 OOXML 測試資產、docx4j / python-docx 測試資源。
- **270 份擴充檔案** —— 包含產生的病態表格（3 層以上巢狀、跨頁表格、交錯合併、自動調整 autofit、欄內表格、多段落與包含清單的儲存格），由 `scripts/verify_corpus.py` 強制執行各項特性的覆蓋額數。
- 每個檔案在 `corpus/manifest.json` 中皆附帶授權條目；閘門拒絕無說明／未知的授權字串——必須具備 SPDX id *加上* 具體來源出處。

閘門將「完成」的定義編碼成型：每份未隔離的檔案皆必須維持 byte-identical roundtrip——任何單一檔案漂移即會讓 `roundtrip --check` 出現紅燈——且任何排除的項目皆*附帶書面原因*進行隔離，並在每個摘要中分開計數。這也是為何路線圖指出後續功能「依語料庫失敗分群排序」：由 render-lab 比對排列出接下來要修復的損壞項目，而非依照功能時程表。

## 為什麼選擇 Rust，又為什麼自行開發 ZIP 層？

選擇 Rust 出於引擎常見的理由（在打字路徑中沒有 GC 停頓、wasm 作為第一級的第二目標、敢於對如此龐大的規格進行重構）——但自行開發 ZIP 的決定才是關鍵所在。現成的 ZIP 函式庫會*解碼並重新編碼*：它們讓各條目走過自己的物件模型並輸出全新的壓縮檔，這正是無損承諾所禁止的暗中重寫行為。因此 `core/ooxml` 直接解析 ZIP 紀錄——local header、central directory、額外欄位、data descriptor、間隙、封包註解——並逐字重新輸出未觸碰的位元組。依賴清單縮減為 `flate2`（deflate）與 `crc32fast`。若位元組層級的保真度是專案承諾，格式程式碼就必須由專案自行掌控。

## 為什麼 CLI 輸出是中文？

該引擎的開發語言為繁體中文（UI 字串、註解、CI 步驟名稱），並搭配英文文件，呼應程式庫的雙語 README 慣例。輸出*格式*（display list JSON、`pagebreaks.json`、diff 報告結構）與語系無關且維持穩定；僅面向人類閱讀的說明文字為中文優先。面向英文的輸出是公開發布階段的修飾項目，而非引擎層級的變更。（[CLI 參考手冊](./cli-reference) 逐字呈現擷取輸出，因此你所讀到的即是工具所印出的內容。）

## 如何保證 CLI 與瀏覽器呈現「相同頁面」？

它們並非各自實作排版。兩個外殼皆使用核心的 `PageDisplayList` JSON——來自相同 Rust 程式碼的相同位元組，分別編譯至原生與 wasm32。塑形使用內建的字型度量（`swash`，不進行系統字型搜尋），因此分頁結果不會因平台而產生漂移，且 golden 斷行點快照在 CI 中釘固了斷行與分頁決策。若渲染器與引擎結果不一致，屬於渲染器的 bug。

## 我現在可以在產品中使用 Quire 嗎？

引擎本身：可以——Apache-2.0 原始碼，`quire-engine` 作為函式庫，`quire-cli` 用於 pipeline，以及供瀏覽器使用的 wasm 外殼（無損保證與 CI 閘門即是約束我們的契約）。目前尚不存在的是編輯介面：目前的引擎支援讀取／渲染／roundtrip，而 editing API 是下一個引擎里程碑。圍繞該引擎的產品線（瀏覽器編輯器、Tauri 桌面應用程式、可自架的協同伺服器）已列於公開路線圖中。

## 路線圖討論／issue 追蹤在哪裡？

請至 [`quire-office/quire`](https://github.com/quire-office/quire/issues) 提交 issue。以語料庫為導向的 bug 是最具行動力的類型——附上 `.docx` 與在其上執行 `roundtrip --check` 的輸出，報告便已完成了一半。
